# 01 — Repair Index After a Missing Search Result

Status: ready-for-agent
Category: bug
Priority: high
Blocked by: None

## Reported Behavior

A search for `Kalanderlerche` returned four indexed results, then TAGGER reported `Error: File not found` for one result.

## Requested Behavior

- Treat a missing search-result file as a stale-result index-repair signal.
- Start a background stale-result index repair for the relevant root.
- Remove the missing path from the SQLite index.
- Index independently discovered paths and their current tags, without identifying filesystem renames.

## Terminology

A **stale-result index repair** is a background root-index refresh triggered because TAGGER cannot read a path returned by an active indexed search. It is distinct from, and must not use, the IPTC-empty filter's future `:resync` command.

## Resolved Triage

- A repair starts only when a selected, active database-search result fails its metadata read with an explicit missing-file error and a cheap existence check confirms that its path is absent.
- The repair refreshes the root that produced that accepted search result. It uses the existing serial root queue, runs behind already queued writes, and at most one repair may run or be queued per root.
- Once queued, repair completes for index integrity even if its search or Photo Workspace becomes obsolete. It must not update obsolete UI state.
- After a successful repair, TAGGER reruns the query only when its root, workspace generation, and query remain current. The replacement result is applied atomically.
- Repair progress, completion, and failure use a persistent non-blocking secondary footer line. Ordinary footer feedback remains readable and usable during the repair.
- A scan may independently discover and index a new path, but does not establish rename identity.
- Tagging, selection, and preview remain usable. Confirmed metadata updates are serialized after the refresh and must win over older index state.

## Agent Brief

**Category:** bug
**Summary:** Repair an active indexed-search result when its selected path no longer exists.

**Current behavior:**
A search result can retain a path after its photo is moved, renamed, or deleted. Selecting that path causes its metadata read to report a missing-file error. TAGGER presents the generic error and leaves the stale path in the result; it does not repair the index.

**Desired behavior:**
When the currently selected path in an active database-search result reports an explicit missing-file error, TAGGER must cheaply confirm that the path is absent, then start a stale-result index repair for the root that produced the accepted search result. The repair is a full root refresh: it removes absent rows and indexes independently discovered files with their current metadata. It must not claim to identify a renamed file.

Only one stale-result repair may be pending or running for a root. It runs in the existing per-root serial queue after previously queued writes, and completes for index integrity even if the user has since changed the search or Photo Workspace. Selection, preview, and normal tagging must remain usable; metadata updates confirmed while repair runs must be reflected after the refresh.

If repair completes while the original root, workspace generation, and query are still current, rerun that query and atomically apply its results. Otherwise, do not change the current Photo Workspace or its ordinary feedback.

Use a persistent, non-blocking secondary footer line for repair progress, success, and failure, so regular footer messages remain readable while the repair is active. Do not show the generic blocking missing-file dialog for this repair trigger.

**Key interfaces:**
- Active database-search request identity — supplies the root, query, and workspace-generation eligibility for triggering and applying repair.
- Background index coordinator — queues and deduplicates stale-result full-root repairs using the existing serial root write queue.
- Root index refresh — removes absent index rows and indexes independently discovered supported photo paths; it provides no rename identity.
- Photo Workspace result application — accepts a refreshed query result only when the original search remains current.
- Footer status presentation — provides repair-specific persistent, non-blocking feedback without replacing ordinary status messages.

**Acceptance criteria:**
- [ ] An explicit missing-file metadata-read failure for a selected current database-search result, confirmed by a path-existence check, schedules one full repair for that search request's root.
- [ ] Missing-file failures outside the active database-search-result condition, and non-missing metadata-read failures, do not schedule repair.
- [ ] Repeated missing results for one root while a repair is pending or running do not schedule another repair.
- [ ] The repair runs behind existing root writes, removes rows for absent photos, and indexes independently discovered supported photos with their current tags; it does not infer or report rename identity.
- [ ] Selection, preview, and tag writes remain usable during repair, and confirmed tag metadata queued during repair is reflected after it completes.
- [ ] If the same root, workspace generation, and query remain current on successful repair, TAGGER reruns the query and atomically replaces the result view; otherwise, repair completion does not alter the current view or ordinary status feedback.
- [ ] Repair progress, completion, and failure appear on a persistent non-blocking secondary footer line while ordinary footer messages remain available; the triggering missing-file condition does not show a blocking error dialog.
- [ ] Tests cover deleted results, independently discovered matching paths, deduplication, queued metadata updates, repair failure, and completion after a superseded/departed search.

**Out of scope:**
- Detecting or reporting filesystem rename identity.
- The IPTC-empty filter's `:resync` command or behavior.
- General resumable or progress-reporting redesign for all index refreshes.
